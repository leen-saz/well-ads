# Review of `main`, November 2026

Scope: tenant isolation, permissions, secrets in logs and responses, number correctness, dead code and migrations,
public-repo hygiene. About 40 PRs merged on 2026-11-03 after quick reads, so this is a line-by-line pass over what is
on `main`. Every item below was reproduced (a failing test or a script run against the code) before it was written
here; things that could not be reproduced were dropped. The repo and its Actions logs are public, so every
reproduction uses synthetic data.

Status column: **open** until a PR is linked, **fixed (#n)**, or **explained** (why it stays).
Severity: *latent* means it needs a second company in `companies` to be exploitable. Today only Well exists, so it
cannot be hit yet, but the product is SaaS by design and the next company turns it on.

## Checked and fine

- Every `scoped()` call: the company is a UUID checked by regex (`src/lib/tenant.ts`), so no filter injection.
- Social, content, journeys: Well's Vault keys are never used for another company (`tokensFor`, `runSocial`, journeys workflow).
- Social posts, knowledge, brand assets, copy, listening, journeys, content, motion videos: reads, patches and deletes carry `company_id`; inserts take the company from the session, never from the body.
- Admin routes: reads and patches of profiles and companies use the session's company; an owner cannot touch another company's user.
- Sessions: HMAC cookie, constant-time verify, API re-reads the profile on every call, disabled users are logged out.
- `safePath` blocks open redirects; the same-origin check requires Origin or Sec-Fetch-Site on every mutating call that sets `write`.

## Decisions for the owner (these change numbers, so nothing was changed)

- **R-19, suggestion windows.** Today `pipeline/modules/suggest/run.py` takes "last 7 days" as the 7 full days plus today's partial day (and `targets` takes 31 days), while the dashboard shows `end-6..end`. *Proposed fix:* cap the windows at `range.end` (`d7 = end-6`, `d30 = end-29`). *Effect:* the evidence on suggestion cards ("spend, days") matches the dashboard for the same period, and the kill and `budget_up` thresholds stop firing on a partial day whose leads still lag. Spend totals in suggestions drop by about one day's worth; some borderline suggestions stop appearing. No dashboard number changes.
- **R-20, outcomes dates.** `pipeline/modules/outcomes/run.py` uses UTC `date.today()` and a UTC `decided_at` against Riyadh data days. *Proposed fix:* convert `decided_at` to Riyadh and use `range.today`. *Effect:* a decision taken between 21:00 and 24:00 UTC no longer counts the day before it as "after"; the 3- and 7-day outcome comparisons shift by at most one day for those decisions.
- **R-21, second payment.** `pipeline/crm/join.py` appends a duplicate lead row for a second payment while its comment says the lead stays counted once; the dashboard uses that count as the close-rate denominator. *Proposed fix (if the comment is the intent):* do not add a lead row for a repeat payment, only the amount. *Effect:* `crmLeads` falls by the number of repeat payers and the close rate rises accordingly. If counting repeat payments as leads is intended, only the comment is wrong. Needs the owner to say which.
